# Confirm a marketplace-installed plugin puts bin/ on the Bash tool's PATH

## Purpose

Establish whether a Squiz installed with `/plugin install`, rather than loaded with `--plugin-dir`, still puts `bin/` on the Bash tool's `PATH`, which is the only route the coding agent's commands have to the binary.

## Acceptance criteria

- [ ] Squiz is installed the way § 9 describes — `/plugin marketplace add`, then `/plugin install` — in an interactive session, which is a person's action rather than a flag.
- [ ] `command -v squiz` is run from the Bash tool in that session and the path it prints is recorded, along with where the entry sits in `PATH`.
- [ ] A subagent is stopped in that session and the `SubagentStop` hook is observed to run: `hook_response` carries `"exit_code": 0` and `"outcome": "success"`, so `${CLAUDE_PLUGIN_ROOT}` resolves under an install as well as under `--plugin-dir`.
- [ ] `docs/notes/the-hook-shell-does-not-get-the-plugin-bin-on-path.md` has its first limit replaced by the measurement, naming the Claude Code version.

## Reference

`docs/notes/the-hook-shell-does-not-get-the-plugin-bin-on-path.md`, under Limits. Everything recorded there was measured with `claude --plugin-dir ./`, where the Bash tool resolved `squiz` to the plugin's own `bin/squiz` and the hook's own `PATH` held nothing the plugin had added.

The hook registration does not depend on the answer, because it goes through `${CLAUDE_PLUGIN_ROOT}` rather than the name. `squiz threads`, `squiz reply` and `squiz resolve` do: § 6 has them run by name from the Bash tool, so an install that does not extend that `PATH` would leave the coding agent unable to work the threads. M3 builds those commands and M9 is the milestone that installs, so the answer is wanted before either closes.
