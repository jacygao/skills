# Remove from spec § 1 and § 2 what the specification does not need

## Purpose

Remove from § 1 Purpose and § 2 Dependencies everything an agent reading the specification does not need to build or review the code, so the section says what the code must do and nothing else.

## What goes

A sentence goes when it fails this test: an agent building or reviewing this part would build or judge it differently without it. These usually fail it:

- **How something came to be known**: measurements, timings, versions a fact was verified against, which run showed what. The spec keeps the conclusion. The evidence goes to a note in `docs/notes/`, unless one already holds it.
- **History**: what an earlier design did, what a milestone removed, "until", "no longer", "since 0.57".
- **Open questions and unmeasured lists.** Each becomes an issue, or one sentence naming the gap where the requirement depends on it.
- **A fact stated twice.** It stays in the section that owns it, and goes from the others.
- **Argument past the one reason a reader needs**, and anything code-level the spec has no reason to fix, such as function names.

What stays: every requirement, every rule, every value a test or the code relies on, and the one reason that stops a reader from undoing a decision.

## Acceptance criteria

- [ ] No requirement, rule, bound, default, exit status, or format changes. The pull request lists each removed passage, grouped by which kind above it was, and where its content went: a note, an issue, the section that owns it, or nowhere, with the reason.
- [ ] Prose is not compressed to save lines. A passage that stays reads as plain sentences, as the `writing-specs` skill sets out. Lines go by removing content, not by shortening it.
- [ ] Every reference into a removed passage, from elsewhere in the spec, from `docs/specs/milestones.md`, or from a code comment, still resolves or is removed.
- [ ] The specification's version is bumped. The other cleanup issues run in parallel and also bump it, so whichever merges second rebases and bumps again.
- [ ] § 2 Verified against: the versions each dependency was verified against are evidence. Decide, and say in the pull request, whether any of them is a requirement, such as a minimum version.
